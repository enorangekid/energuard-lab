# 에너가드랩 쇼핑 순위 수집 확장프로그램

네이버 쇼핑 검색 API 종료 이후 직원의 실제 Chrome 세션에서 일반 상품 순위를 읽어
기존 Supabase `keyword_rank_history` 테이블에 저장하는 반자동 수집기입니다.

## 설치

1. Chrome 주소창에 `chrome://extensions`를 입력합니다.
2. 우측 상단의 **개발자 모드**를 켭니다.
3. **압축해제된 확장 프로그램을 로드합니다**를 누릅니다.
4. 이 `shopping-rank-extension` 폴더를 선택합니다.
5. 네이버에 로그인한 뒤 확장프로그램을 고정합니다.

## 사용

1. 에너가드랩의 **키워드 분석 > 키워드 일괄 수집**을 엽니다.
2. 메인·보조 키워드를 선택하고 **선택한 키워드 수집 시작**을 누릅니다.
3. 선택한 스토어와 키워드 구분이 확장프로그램으로 자동 전달됩니다.
4. 확장프로그램이 여는 수집 탭과 네이버 쇼핑 탭을 완료 전까지 닫지 않습니다.

확장프로그램 아이콘에는 팝업이 없습니다(2026-08-06 제거) — 판다랭크처럼 아이콘을 눌러도 아무것도
뜨지 않고, 수집은 전부 에너가드랩 화면(키워드 일괄 수집 / 아이템 추적 일괄조회)에서만 시작합니다.
과거에 팝업에 있던 "상품 URL 빠른 확인" 단건 조회 기능은 대응하는 화면이 없어 함께 제거했습니다 —
필요해지면 에너가드랩 쪽에 새로 추가할 것.

확장프로그램은 장시간 수집 중 Chrome 백그라운드 작업이 종료되는 문제를 피하기 위해
`에너가드랩 쇼핑 순위 수집` 전용 탭을 함께 유지합니다. 수집 완료 전까지 두 탭을 닫지 마세요.

광고 상품은 `data-shp-contents-grp="ad"` 및 `SA_prod` 속성으로 제외하고,
일반 상품의 `organic_expose_order`를 우선 사용합니다. 기본 검색 결과를 기준으로 하므로
`npayType` 같은 별도 상품 필터는 적용하지 않습니다.

코드를 갱신한 뒤에는 `chrome://extensions`에서 이 확장프로그램의 새로고침 버튼을 누른 후
다시 수집해야 변경된 카드 식별 및 순위 계산 로직이 적용됩니다.

## 현재 제한

- Chrome이 실행 중이고 네이버 세션이 정상이어야 합니다.
- 캡차나 접속 제한이 나오면 자동으로 우회하지 않습니다.
- 네이버가 `data-shp-*` 계약까지 변경하면 수집기 업데이트가 필요합니다.
- 자동 cron 대신 직원이 버튼을 눌러 실행하는 방식입니다.

## 빠른 수집(백그라운드 fetch) — 2026-08-06 도입

일반 배치 수집(`runCollection`)과 아이템추적 수집(`runTrackedItemsBatchLookup`) 둘 다,
탭을 열어 렌더링을 기다리는 대신 **탭 없이 `fetch()`로 검색결과 HTML을 직접 받아오는 빠른
경로를 먼저 시도**하고, 캡차·차단·파싱 실패 시에만 기존 탭 방식으로 자동 폴백한다
(판다랭크 확장프로그램을 리버스엔지니어링해서 참고, 코드는 새로 작성).

- 원리: `chrome.declarativeNetRequest`로 `sec-fetch-*`/`referer` 헤더를 실제 페이지 이동처럼
  위장한 뒤 `fetch(url, {credentials:"include"})`로 검색결과 페이지의 raw HTML을 받는다.
  HTML 안에 이미 `__NEXT_DATA__`로 상품 데이터가 박혀있어 `parser-core.js`(RankParser)를
  그대로 재사용해 파싱한다(`background.js`의 `fastFetchSearchPage`/`fastFetchSearchPages`).
- `pagingSize`는 반드시 **40** — `RankParser.resolveOrganicRank`가 "한 페이지=40개"를 전제로
  2페이지부터 절대 순위를 계산한다. 80 등으로 바꾸면 2페이지부터 순위가 틀어진다.
- 이 raw HTML의 `__NEXT_DATA__`엔 스토어 자체 상품코드(`chnl_prod_no`)가 안 들어있고 네이버
  통합ID(`nvMid`)만 있다 — 상품 링크(`smartstore.naver.com/main/products/{코드}`)에서 진짜
  코드를 역추출해서 보정한다.
- 페이지 사이 대기는 1~2초(랜덤) — 원래 0.4~0.8초로 판다랭크보다 짧게 잡았는데, 82개 키워드
  배치 수집에서 캡차(HTTP 418)가 첫 키워드부터 걸려서 실행 전체가 탭 방식으로 폴백되는 문제가
  발생했다(2026-08-06). 서비스워커 콘솔에 실제 418 응답을 로그로 확인한 뒤 원인을 좁혀보니,
  같은 세션·같은 URL로 실제 탭 이동은 캡차 없이 통과되는데 fetch()만 막히는 걸로 봐서 단순
  IP 차단은 아니었고, **키워드가 바뀔 때 대기가 전혀 없던 게(페이지 사이에만 대기, 키워드
  전환 시점엔 0초) 실제 원인에 가까워 보였다** — 판다랭크 수준(1~2초)으로 늘리고, 키워드
  전환 시점에도 fast 경로를 썼으면 반드시 쉬도록 `runCollection`/`runTrackedItemsBatchLookup`
  둘 다 수정.
- 아이템추적은 200위(5페이지)까지만 스캔한다 — 1000위까지 늘려봤으나 페이지당 대기가 누적돼
  키워드당 너무 오래 걸렸고, 판다랭크도 실측상 200위 근방(148~160위)에서 끝나는 걸로 보여
  기존 관례로 되돌림.

## 메인/보조 키워드 일괄 수집에 검색량도 같이 저장 — 2026-08-06 도입

`runCollection`이 키워드마다(페이지 수와 무관하게 키워드당 1번) `naver-rank` 엣지함수의
`keywordInsight` 액션(검색광고 API, 순위 스캔과 별개라 살아있음)을 호출해서 그 키워드의 월간
검색량(PC/모바일/합계)을 `keyword_rank_history`의 `search_volume_pc/mobile/total` 컬럼에
같이 저장한다. `keywordInsight` 호출 자체가 서버에서 `keyword_search_volume_monthly`(에너가드랩
"키워드 분석"·확장프로그램 키워드 인사이트 패널이 같이 쓰는 월별 검색량 테이블)에도 이번 달
검색량을 자동으로 남기므로, 그쪽 테이블도 배치 수집 때마다 같이 채워진다. 검색량 조회가
실패해도 순위 저장 자체엔 영향 없음(에러를 삼키고 `null`로 남김).

## keywordInsight 레이스 컨디션 수정 — 2026-08-06

`service-worker.js`의 `fetchKeywordInsight()`가 "검색량 저장" 요청과 "추이 조회" 요청을
`Promise.all`로 동시에 쏘고 있었다. 이번 달 그 키워드를 처음 조회하는 순간엔 저장이 끝나기
전에 추이 조회가 먼저 도착해서, 방금 막 만든 이번 달 검색량 값을 그래프가 못 보고 그리는
경우가 있었다(사용자가 검색해서 값이 DB엔 있는데 그래프엔 안 나오는 걸로 확인됨). 두 요청을
순차로(저장 먼저, 조회 나중) 바꿔서 이 레이스를 없앴다.

## 스마트스토어 관리자 순위 진단 수집 — 제거함 (2026-08-06)

`sell.smartstore.naver.com`의 "검색 순위 진단" 관리자 화면을 스크레이핑해서
`keyword_rank_history`에 `source: "naver_diagnosis"`로 저장하던 기능(팝업의 "관리자 순위
가져오기" 버튼, rank-tracker.html의 "네이버스토어 순위 수집" 버튼)을 완전히 제거했다.

- 제거 이유: 위 "빠른 수집" 도입으로 **알고 있는 키워드의 실시간 순위 확인은 이 방식이 훨씬
  빠르고 정확**해졌고, 이 기능의 차별점이던 "네이버가 대신 찾아주는 미등록 키워드 발견"은
  실사용 결과 의미 있는 신규 키워드가 거의 안 나와 카드에 종류만 늘리는 노이즈로 판단됨.
  코드도 700줄 넘게 복잡하고(관리자 화면 구조가 바뀔 때마다 계속 손봐야 했음) 유지보수 부담이
  실익보다 컸음.
- 삭제된 파일: `smartstore-collector.js`, `smartstore-network-tap.js`.
- `keyword_rank_history`에 남아있는 과거 `source: "naver_diagnosis"` 행은 그대로 두었다
  (읽기 전용 이력이라 삭제 안 함) — rank-tracker.html의 "주목" 배지 표시 로직도 안 건드렸으니
  과거 데이터는 계속 정상적으로 보인다. 앞으로 새로 쌓이지만 않을 뿐이다.

## N+스토어 순위 — 교차검증 재시도로 실사용 가능, fast-fetch는 재실패 (2026-08-26)

팝업의 **수집 채널**을 "네이버플러스스토어"로 바꾸면 가격비교 대신
`search.shopping.naver.com/ns/search`(네이버플러스스토어 검색)의 순위를 수집한다.

**교차검증 재시도(성공)**: 아래 "최종 결론"에서 미뤄뒀던 재시도 로직을
`runNplusStoreCollection`(background.js)에 구현했다. 매 시도마다 탭을 새로 내비게이션하고,
우리 스토어 상품들의 "상품코드:순위" 조합이 2번 연속 똑같이 나오면 그 값을 채택한다(최대 3회
시도, `NPLUS_MAX_ATTEMPTS`). 3회 안에 안정화 안 되면 마지막 시도 값을 그대로 쓰고 "불안정"
표시를 남긴다. 실제 테스트에서 정상 작동 확인 — 현재 이 방식으로 실사용 중.

**tab 없는 fast-fetch(재실패, 되돌림)**: 네이버 일반쇼핑(가격비교)의 declarativeNetRequest
헤더위장 기법을 `ns/search`에도 적용해봤다(2026-08-26, 커밋 `4c85918`~`24e8a99`, 이후
`d160f8f`에서 전부 revert). fetch 자체는 성공해서 카드를 가져왔고, 몰 이름 추출 위치도
사용자가 직접 캡처해준 실제 카드 HTML(`<span class="mallLink_mall_name__해시">`)로 정확히
찾아냈다 — 그런데도 "우리 스토어가 안 잡힌다"는 결과가 반복됐다. 원인은 코드 버그가 아니라
**fetch가 최초 화면(스크롤 전, 20~40개 남짓) 한 장만 가져오는데, 그 한 장의 렌더링 자체가
매번 달라진다**(바로 이 문서 "최종 결론"의 그 비결정성)는 것 — 실제로 2위 상품이 있는데도
특정 순간의 fetch에는 안 잡히는 사례를 실측으로 확인했다. 즉 tab 없이는 "최초 화면 한 장"이라는
불안정한 샘플에 의존할 수밖에 없어서, 이 접근 자체가 N+스토어에는 안 맞는다고 결론 내리고
전부 되돌렸다 — 경쟁사(셀러랭크) 확장프로그램도 애초에 fetch를 시도하지 않고 항상 탭을
쓰는 이유가 아마 이것과 같을 것으로 추정된다.

**광고 슬롯 수집(2026-08-31 추가)**: 순위 계산할 때 걸러내던 `isAd: true` 레코드(광고주 몰
이름·노출순서)를 `saveAdSlotSnapshot`(background.js)이 `ad_slot_snapshots` 테이블에 별도
저장한다. `coupang-rank.html` 베타 페이지의 "키워드별 광고 압박도"(키워드당 자연순위·상단광고
수·광고주 수 + 높음/보통/낮음 배지)와 "경쟁사 광고 강도 리더보드"(몰별 최근 30일 노출횟수 +
급증/유지/급감 추세)가 이 테이블을 읽어서 그린다. 기존 N+스토어 순위 수집(`runNplusStoreCollection`)
안에서 이미 파싱해두던 `products` 배열을 그대로 재사용하므로 **추가 스크래핑 비용이 없다** —
"검색 시작"으로 N+스토어를 수집할 때마다 같이 채워진다. 압박도 배지 기준(상단광고 3개↑=높음)과
리더보드 급증/급감 기준(최근 30일 대비 이전 30일 1.5배↑/0.5배↓)은 잠정치로, `coupang-rank.html`
상단 상수(`AD_PRESSURE_HIGH_THRESHOLD` 등, `adTrendLabel`)에서 조정 가능.

### 왜 만들었나
가격비교와는 **다른 별개의 랭킹**(프로모션/멤버십 맥락이 섞인 결과셋)이라 대체재는 아니고,
페이지 이동이 아니라 스크롤로 이어지는 무한스크롤(cursor 페이지네이션) 구조라 탭 재로딩 없이
스크롤만으로 배치를 모을 수 있어 빠르게 수집될 걸로 기대하고 시도했다.

### 구조
- 최초 화면(서버 렌더링분)은 DOM(`data-shp-*`)에서, 스크롤로 새로 뜨는 배치는
  `paged-composite-cards` 네트워크 응답에서 잡아 합친다(`nplus-collector.js`).
- 저장은 같은 `keyword_rank_history` 테이블에 `source: "nplus_store"`로 분리(가격비교
  `curated`/관리자 진단 `naver_diagnosis`와 안 섞임).
- 결과 확인용 `nplus-report.html`/`nplus-report.js` — 수집 완료 시 자동으로 새 탭에 열림.

### 실측으로 확인·수정한 버그들 (전부 고쳐도 결국 불안정했음)
1. DOM 추출과 네트워크 추출의 상품 식별 키 우선순위가 달라(`nvMid` vs `chnl_prod_no`) 같은
   상품이 두 번 카운트됨 → 두 경로 모두 `channelProductId`(chnl_prod_no) 우선으로 통일.
2. N+스토어 카드의 `data-shp-contents-dtl`엔 몰 이름(`chnl_prod_nm`) 필드 자체가 없음 → 카드
   루트에서 화면 텍스트로 스토어명을 직접 검색하도록 변경.
3. 자동화 URL에 `sort=RECOMMEND`가 빠져 있어 실제 브라우징과 다른 결과셋을 받음 → 명시 추가.
4. **가장 큰 원인**: `a[data-shp-contents-grp][data-shp-contents-dtl]` 선택자가 진짜 상품
   카드뿐 아니라 GNB(상단 내비게이션)·rec1(연관검색어 추천칩)·sch(자동완성 검색어) 같은
   비상품 위젯까지 잡아서 순위가 15~40 정도씩 밀림 → `data-shp-inventory==="prod"`인 것만
   상품으로 인정하도록 필터 추가.
5. 최초화면 "안정화" 판단을 전체 앵커 개수로 하다 보니 GNB/rec1/sch(먼저 뜨고 먼저 안정됨)만
   보고 "다 됐다"고 착각해 진짜 상품 그리드가 로딩 중인데 너무 일찍 추출 → 상품 카드
   개수(`inventory="prod"`)만으로 안정화 판단하도록 변경.

### 최종 결론 (2026-08-06)
5가지를 전부 고친 뒤에도 **같은 키워드를 반복 수집하면 순위가 매번 들쭉날쭉했다**(한 번은
1위로 정확히 나왔다가 바로 다음 실행엔 완전히 다른 상품이 1위로 나오는 식). 이건 로직 버그가
아니라 **페이지 자체가 로드될 때마다 광고/위젯 렌더링 타이밍이 비결정적**이라는 뜻으로 보인다.
안정화하려면 초기화면을 여러 번 반복 추출해 서로 일치할 때까지 재시도하는 교차검증 로직이
필요한데, 지금까지 들인 시간 대비 추가 투자 가치가 낮다고 판단해 **사용자 요청으로 여기서
중단**했다. 코드는 재개할 경우를 대비해 그대로 남겨둔다 — 다음에 이어서 손댈 일이 생기면
"교차검증 재시도" 부분부터 설계할 것.
